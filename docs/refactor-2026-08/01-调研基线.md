# AHA 结构重构 — 调研基线

> 目的：记录对 AHA 数据结构和运行模型的完整认知，作为重构方案的输入。
> 状态：调研完成，事实均已实测验证。
> 日期：2026-08-14

## 1. 真实 AHA home 目录结构

实测路径（Windows 单副本，WSL 视角 `/mnt/c/Users/toope/.aha`）：

```
<AHA home>/
├── config.json              # 全局配置
├── runs/<run_id>/           # 每个 run 一个目录
│   ├── plan.json            # run 计划 = task 权威副本
│   ├── events.jsonl         # 全 run 事件流（27 个模块写入）
│   ├── inbox/{target}.jsonl # 消息队列，按 target 隔离（main/browser/aha/sub-N）
│   ├── chat/{agent}-{hash}.md
│   ├── sessions/{agent}.json
│   ├── tasks/{task_id}/
│   │   ├── task.json        # task 副本（与 plan.json 同构，冗余）
│   │   ├── messages.jsonl
│   │   ├── prompts/         # 每次 prompt 快照
│   │   ├── sessions/{agent}.json
│   │   ├── rounds/
│   │   └── artifacts/
│   └── runtime/
│       ├── backend-{task}-{agent}.json   # 后端进程状态
│       ├── chat-offset-{task}-{agent}.json # 字节消费游标
│       └── chat-consumer-{task}-{agent}.lock
├── knowledge/               # KB（git 仓库）
│   └── projects/<project_key>/{navigation,worklog,solutions,...}
├── runtime/                 # AHA home 级进程状态
├── wsl-backends.json        # WSL 探测缓存
├── browser/ feishu/ hardware/ weixin/   # 通道状态
```

## 2. 进程模型

| 进程 | 职责 | 平台 |
|---|---|---|
| AHA Web 服务 | HTTP API、UI、消息路由、slash 命令 | Windows（pythonw） |
| 后端 agent（每 task 一个） | `claude-chat/codex-chat <run_id> <target> --task-id <task_id>` | Windows 或 WSL |
| 各类 bridge | browser/hardware/observe_proxy | 各自 |

- 每个 task 一个独立后端进程
- 所有 task **共享 run 级 inbox 和 events.jsonl**
- WSL 后端：`wsl.exe` 是 Windows 宿主，WSL 内 python/claude 是实际工作进程

## 3. 核心数据结构（schema）

### config.json
- `backend`, `default_parallel`, `workspace_roots`（Windows 视角，含 UNC）
- `providers[]`（id/name/base_url/auth_style/credential）
- `configured_models[]`（provider_id/model_id/backend/wire_api/context_window/role models）
- `codex`/`claude`（bin/model/env[] 含 API key）
- `knowledge`（path=`~/.aha/knowledge`，git，retrieval）
- `integrations`（feishu/weixin/observe_proxy/headroom）

### plan.json
- run 级：`goal`, `mode`, `main_agent`, `tasks[]`
- task 级：`id`, `title`, `workspace_path`, `preferred_*`, `collaboration_mode`, `agents[]`, `status`, `prompt_file`, `output_file`, `log_file`, `inbox_file`

### task.json（tasks/{id}/task.json）
- 与 plan.json 里 task 同构（冗余副本）

### backend state（runtime/backend-{task}-{agent}.json）
- `target`, `task_id`, `backend`, `status`, `pid`, `command`, `model`, `resolved_model`, `started_at`, `stopped_at`, `wsl_distro`, `wsl_native_home`

### session（tasks/{id}/sessions/{agent}.json）
- `backend_session_id`, `history_backend_sessions`, `compact_summary`, `workspace_path`, `status`, `model`

### chat-offset（runtime/chat-offset-{task}-{agent}.json）
- `offset`（字节游标指向 inbox）, `updated_at`

## 4. 数据流

```
用户消息 → append_message → inbox/{target}.jsonl（task_id 在 payload）
    ↓
task 后端 agent_chat:
    load_chat_offset → iter_jsonl_records_from(inbox, offset)
    → worker_task_id 过滤 → next_task_message_batch（逐组）
    → 生成 prompt → 调 claude/codex → 写 events + chat/*.md
    → save_chat_offset（推进）
    ↓
interrupt: stop_backend + save_chat_offset(推进到 inbox 末尾) + set_agent_status
```

## 5. 已确认的结构性缺陷（根因）

### 缺陷 1：inbox 不按 task 隔离（串台根因）
- `inbox/main.jsonl` 实测含 10 个 task 的消息混合
- 每 task 用自己的 offset 读同一 inbox，offset 互相跨越对方消息
- 兜底靠 `worker_task_id` 过滤 + 逐组处理，但并发 main 任务时仍延迟/错位

### 缺陷 2：task 数据冗余无一致边界
- `plan.json` 和 `tasks/{id}/task.json` 双份，靠同步维持
- inbox 在 run 级，messages.jsonl 在 task 级，关系不清晰

### 缺陷 3：路径无统一抽象
- 配置存 Windows 视角（`D:\tmp\`、UNC、`~`），WSL 消费靠零散补丁
- 已建 `host_native_path` 但未全面收敛

### 缺陷 4：进程生命周期管理分散
- interrupt/recover/offset 推进散在 `task_command_actions.py`、`status.py`、`chat.py`
- 后端 pid 语义跨平台混乱（wsl.exe 宿主 vs WSL 内工作进程）
