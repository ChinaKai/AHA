# AHA 结构重构方案

> 目的：修复 AHA 在"多任务并发 + WSL/Windows 双平台 + 多进程"现实下的结构性缺陷。
> 状态：方案设计（待实施）。
> 日期：2026-08-14
> 原则：渐进式重构，每层独立可验证、可回滚，避免一次性大爆炸。

## 0. 问题总览

AHA 的核心数据模型和进程模型是**单用户、单任务、单平台**假设下设计的，但现实是：

- **多 task 并发**：同 run 多个 task 的 main agent 并行运行
- **双平台**：Web 服务在 Windows，后端 agent 可能在 WSL
- **多进程**：每 task 一个后端进程 + Web 服务 + 各类 bridge

本次会话已修 11 个表层 bug（见 01-调研基线 §6），但根因是以下 4 个结构缺陷。

## 1. 四个结构性缺陷

### 缺陷 1：inbox 不按 task 隔离（串台根因）

**现状**：
- `inbox_path(root, run_id, target)` 只按 target 隔离 → `inbox/main.jsonl` 被所有 main task 共享
- offset 文件按 task 隔离（`chat-offset-{task}-{target}.json`），但指向共享 inbox
- 每 task 用自己的 offset 读同一 inbox，offset 互相跨越对方消息
- 兜底靠 `worker_task_id` 过滤 + 逐组消费，但并发 main 任务时仍延迟/错位

**证据**：inbox/main.jsonl 实测含 task-001~010 的消息混合。

**根因**：`inbox_path` 设计为"target 队列"，没有 task 维度。但 `append_message` 已经双写 `tasks/{id}/messages.jsonl`（task 隔离）。

**修复方向**：
- 方案 A（推荐）：**inbox 按 task 隔离**。`inbox/{task_id}/{target}.jsonl`，offset 指向 task 专属 inbox。改动 `inbox_path` 签名 + 14 个调用点。
- 方案 B：**直接用 messages.jsonl 作为消费源**。inbox 退化为纯投递队列，后端从 `tasks/{id}/messages.jsonl` 读。改动更大但数据模型更清晰。

**推荐方案 A**（改动小、语义清晰）：inbox 保持"投递队列"角色，但按 task 分文件。

### 缺陷 2：task 数据冗余无一致边界

**现状**：
- `plan.json` 是 task 权威副本，`tasks/{id}/task.json` 是冗余副本
- 同步逻辑散落，可能不一致
- `append_message` 双写 inbox + messages.jsonl，事件流又写 events.jsonl

**修复方向**：明确单一数据源。plan.json 为权威，task.json 作为缓存（或反之）。messages.jsonl 为 task 消息的唯一权威记录，inbox 只是消费游标。

### 缺陷 3：路径无统一抽象

**现状**：
- 配置路径存 Windows 视角（`D:\tmp\`、UNC、`~`）
- WSL 消费靠零散补丁（`host_native_path`/`wsl_workspace_native_path`/`_prompt_workspace_path`）
- 已建 `host_native_path` 但未全面收敛

**修复方向**：建立统一 `AhaPath` 概念，所有配置/存储路径通过它解析。内部处理 `~`、Windows 盘符、UNC、WSL native 四态转换。

### 缺陷 4：进程生命周期管理分散

**现状**：
- interrupt/recover/offset 推进散在 `task_command_actions.py`、`status.py`、`chat.py`
- 后端 pid 语义跨平台混乱（wsl.exe 宿主 vs WSL 内工作进程）
- offset 在 interrupt/recover 时该推进没推进（本次已修一处，但未系统化）

**修复方向**：抽象"后端进程生命周期"为一个概念，interrupt/recover/stop/start/offset 推进作为原子操作。

## 2. 分层重构计划

### 第一层：路径抽象层（最小、收益最大）
- 目标：所有 `Path(x).expanduser()` 收敛到统一解析
- 涉及：`store/ws_target.py`（已有 host_native_path）、`store/paths.py`、各消费点
- 验收：WSL 下所有配置路径解析正确，无散落 expanduser

### 第二层：任务级存储命名空间（根治串台）
- 目标：inbox/offset/messages 按 task 隔离
- 涉及：`store/paths.py`（inbox_path 加 task_id）、`chat.py`、`task_messaging.py`、`chat_offsets.py` 等 14 个调用点
- 验收：两 task 并发 main，消息不串台

### 第三层：进程生命周期抽象（根治进程/offset 问题）
- 目标：interrupt/recover/stop/start/offset 原子化
- 涉及：`task_command_actions.py`、`status.py`、`backend_runtime.py`、`chat.py`
- 验收：interrupt 后 offset 正确推进，无孤儿进程，recover 不误判

## 3. 实施顺序

1. 建立统一路径抽象（`AhaPath`），替换散落 expanduser → 消除一半 WSL bug
2. 重构 inbox 为 task 隔离 → 根治串台
3. 进程生命周期原子化 → 根治 interrupt/recover/offset

## 4. 风险与回滚

- 每层独立提交，可单独回滚
- 第一层最安全（纯路径解析），第三层风险最高
- 迁移期兼容旧路径（读旧 inbox，写新 inbox）

## 5. 验证策略

- 每层：聚焦测试 + 端到端验证（起真实 task）
- 重构后：全量测试
- 关键回归点：WSL 后端启动、并发写锁、context window、interrupt、串台

## 附录 B：第二层 inbox 隔离 — 决策记录

### 决策：放弃 task 级 inbox 隔离，保留共享 inbox + offset 修复

**评估过程**：
- 尝试了 task 级 inbox（`inbox/{task_id}/{target}.jsonl`），改动 14 个调用点，大量测试依赖旧路径，迁移风险高
- 重新分析发现：共享 inbox + `worker_task_id` 过滤 + 正确 offset **已经能工作**
  - agent_chat 按 task_id 过滤消息（`if worker_task_id and item_task_id != worker_task_id: continue`）
  - 每个 task 独立 offset 文件（`chat-offset-{task}-{target}.json`）
  - task-010 的串台问题根因是 interrupt 时 offset 没推进（已修），不是共享 inbox
- **结论**：根治串台的钥匙是"offset 语义正确"，不是"inbox 物理隔离"

**保留的修复**：
- `recover_stale_running_agent` 推进 offset（status.py）— 根治 interrupt 后看不到新消息
- `chat.py` 主循环统一 host_native_path + worker_task_id 提前

**放弃的改动**：
- inbox_path 加 task_id（paths.py）
- 14 个调用点传 task_id

**未来可选项**：若并发 main 任务仍暴露问题，再考虑 task 级 inbox（作为独立大任务）。
